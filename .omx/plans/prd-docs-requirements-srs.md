# PRD — 旅法师卡牌 / 状态栏 / 战斗辅助系统

## 1. 背景
本项目运行在 SillyTavern + Tavern Helper + MVU 变量框架环境中，目标是把现有分散的设计文档收束为可实施、可回写、可扩展的角色卡辅助系统。

当前痛点：
- 设计文档分散，阶段边界不统一
- 冷/热数据和 AI 写入边界需要先锁定
- 普通检定与战斗检定受 one-shot 限制程度不同，必须分流设计
- 若先上完整战斗，容易在数据安全与交互流程上同时失控

## 2. 产品目标
构建一套围绕“旅法师”主题的：
- 状态栏与最新楼层热状态系统
- 正式卡牌仓库与当前可见区过滤系统
- 背包整理为正式卡牌的事务闭环
- 普通检定与战斗检定双模式系统
- 战斗浮窗与终局 CombatLog 回写机制

## 3. 非目标
首版不做：
- 完整 RPG / CRPG 战斗引擎
- 自动任务奖励
- 背包冷藏系统
- 自动离队归档
- 复杂任务树
- 脚本接管全部战斗数值计算
- P1 内引入特殊暗骰 / 多段隐藏检定

## 4. 成功标准
### P0 成功标准
- 能稳定读写最新楼层 MVU
- 状态栏五大项可显示和基础编辑
- 正式卡牌仓库、当前可见区、当前可见卡摘要三层关系成立
- 主聊天 AI 回写被白名单 + Zod 校验保护
- 背包整理失败时无半成功状态
- 历史 DicePool / CombatLog 不再污染后续上下文

### P1 成功标准
- 可以从 `敌方` 启动战斗浮窗
- 战前快照、放弃恢复、锁定机制成立
- 每次战斗检定支持投骰、最多 3 次重 roll、确认后再推演
- AI 负责战斗数值推演，脚本只负责流程与回写
- 战斗终局写入 CombatLog、清空敌方、覆盖近期事务

### P2 成功标准
- 至少一种特殊判定可以工作
- 特殊判定不破坏 P1 主流程
- AI 若申请特殊判定，只能通过结构化请求，不可直接操控脚本

## 5. 用户 / 系统角色
- 玩家：通过状态栏管理热状态、仓库、可见区；在战斗浮窗内进行策略与投骰确认
- 主聊天 AI：负责日常叙事推进、普通检定裁定、合法热数据更新
- 战斗 AI：负责战斗回合叙事与数值推演
- 脚本 / 前端：负责 MVU 访问、变量保护、UI、战斗流程控制、快照与回滚

## 6. 核心决策（ADR）
### Decision
采用 P0 / P1 / P2 分阶段落地：
- P0 先做数据与回写安全闭环
- P1 再做战斗浮窗与战斗回写
- P2 最后做特殊判定

### Decision Drivers
1. 降低首版失败风险
2. 保持 AI 的叙事与战斗推演自由度
3. 与 Tavern Helper / MVU 模板和 util 工具兼容

### Alternatives Considered
- 一次性交付完整战斗：范围过大，否决
- 脚本完整接管战斗结算：自由度与复杂度不平衡，否决
- 普通检定改为系统自动判定：与现有文档主线不一致，否决

### Consequences
- P0 / P1 边界必须严格执行
- latest/-1 楼层语义必须明确，不可直接照搬当前楼层示例
- 特殊判定必须严格后置到 P2

## 7. 范围分期与任务拆解

## P0 — 最小稳定闭环
### P0.1 MVU schema 与变量结构注册
交付物：
- `schema.ts` 设计
- 变量结构注册脚本方案
- 世界书变量条目草案

关键任务：
- 定义世界 / 化身 / 背包 / 任务 / 队伍 / 当前状态 / 当前可见区 / 当前可见卡摘要 / 敌方结构
- 动态集合使用 `z.record`
- 数值清洗使用 clamp / transform
- 变量结构注册脚本只保留 `registerMvuSchema(Schema)` 最小职责

依赖：无

验收：
- schema 幂等解析思路明确
- old/new diff 规则未塞进 schema

### P0.2 最新楼层访问与状态栏架构
交付物：
- 状态栏架构说明
- latest / -1 语义访问方案
- 生命周期方案

关键任务：
- 状态栏采用脚本 + 独立 iframe
- 统一初始化：等待 Mvu -> 等待 stat_data -> mount
- latest/-1 语义替代 `getCurrentMessageId()` 绑定

依赖：P0.1

验收：
- 状态栏稳定面向最新楼层，而非旧楼层
- 生命周期使用 `$(() => {})` 与 `pagehide`

### P0.3 卡牌仓库与当前可见区
交付物：
- 仓库字段说明
- 当前可见区规则
- 摘要复制规则

关键任务：
- 正式卡牌保存在聊天变量
- 当前可见区与摘要保存在 MVU 热数据
- 超预算时给出提示策略
- 删除卡牌时清理摘要与引用

依赖：P0.1, P0.2

验收：
- 仓库不直接进入 prompt
- 只有摘要进入 prompt

### P0.4 主聊天 AI 回写安全链路
交付物：
- 白名单规则表
- parse -> filter -> validate -> replace 链路设计
- DicePool / CombatLog 历史遮蔽规则

关键任务：
- 非法更新拒绝并提示
- HP/MP 非负保护
- 自建 AI 请求必须手动 parse + replace

依赖：P0.1, P0.2

验收：
- 非法更新不静默失败
- 历史 DicePool / CombatLog 不污染上下文

### P0.5 背包整理为正式卡牌
交付物：
- 卡牌整理流程图
- JSON 草案格式
- 回滚规则

关键任务：
- 玩家选物品 + 整理方向
- AI 生成卡牌 JSON 草案
- 清洗校验 + 生成稳定 cardId
- 成功才消耗背包物品
- 失败整包回滚

依赖：P0.1, P0.3, P0.4

验收：
- 不出现“仓库未写入但背包已消耗”

## P1 — 战斗首版闭环
### P1.1 战斗浮窗与战前快照
交付物：
- 战斗浮窗架构方案
- 战前快照 / 锁定机制

依赖：P0 完成

验收：
- 可从 `敌方` 启动战斗
- 放弃后可恢复战前状态

### P1.2 单次战斗检定交互闭环
交付物：
- 投骰 / 重 roll / 确认流程定义

关键任务：
- 玩家输入策略
- 前端/脚本投骰
- 每次战斗检定最多重 roll 3 次
- 玩家确认最终骰面后再发送 AI

依赖：P1.1

验收：
- AI 只看到最终确认后的骰面

### P1.3 战斗 AI 推演与回合回写
交付物：
- 战斗 prompt 结构
- 回合预览 / 回写方案

关键任务：
- AI 负责命中 / 伤害 / 状态 / 掉落等数值推演
- 脚本负责流程、回写、保护
- 中间回合不写主楼层 CombatLog

依赖：P1.2

验收：
- 回合级写回与 UI 状态一致

### P1.4 战斗终局处理
交付物：
- CombatLog 写入规则
- 敌方生命周期闭环规则

关键任务：
- 终局才写 CombatLog
- 清空 `敌方`
- 覆盖 `世界.近期事务`
- 解锁状态栏

依赖：P1.3

验收：
- 终局回写完整且不污染中途流程

## P2 — 高级扩展
### P2.1 手动触发特殊判定
交付物：
- 高难度特殊判定按钮与规则

### P2.2 AI 结构化申请特殊判定
交付物：
- 结构化特殊判定请求格式
- 前端执行器

依赖：P1 完成

验收：
- 特殊判定不破坏 P1 主流程

## 8. 依赖关系总览
```text
P0.1 -> P0.2 -> P0.4 -> P0.5
P0.1 -> P0.3 -> P0.5
P0 完成 -> P1.1 -> P1.2 -> P1.3 -> P1.4
P1 完成 -> P2.1 -> P2.2
```

## 9. 风险与缓解
| 风险 | 影响 | 缓解 |
|---|---|---|
| 状态栏误绑定旧楼层 | 数据写错楼层 | 强制 latest/-1 语义 |
| 仓库泄漏进 prompt | 上下文膨胀 | 仓库与摘要分层 |
| 背包整理半成功 | 数据损坏 | 事务式提交与回滚 |
| MVU 未初始化即读写 | 界面异常 | 等待 Mvu + stat_data ready |
| 战斗中途写主楼层 CombatLog | 聊天污染 | CombatLog 仅终局写入 |
| 特殊判定过早引入 | 主流程不稳 | 严格延后到 P2 |

## 10. 后续建议
- 先以 P0 为执行基线
- P0 验收完成前不进入 P1
- P1 首版只做公开投骰战斗，不做特殊暗骰
- P2 再扩展 GM 式高级判定
