# P0 / P1 / P2 实施清单（基于 deep-interview-docs-requirements-srs.md）

## 1. 使用说明
- 本清单是对 `.omx/specs/deep-interview-docs-requirements-srs.md` 的实施拆分
- 当前仍属于需求/规划产物，不是代码实现记录
- 默认遵守 `.cursor/rules/*.mdc`、AGENTS.md 与 Tavern Helper / MVU 约束

## 2. 总体实施策略
1. 先做 **P0 数据与回写安全闭环**
2. 再做 **P1 战斗浮窗闭环**
3. 最后做 **P2 特殊判定扩展**

所有阶段都应优先复用：
- `util/mvu.ts`
- `util/script.ts`
- `util/streaming.ts`
- `初始模板/角色卡/*`
- `示例/角色卡示例/*`

---

## 3. P0 实施清单（最小稳定闭环）

### P0-1 变量结构与目录基线
**目标**：建立可维护的 MVU schema 与角色卡目录骨架。  
**输入**：SRS 第 4、5、9 节。  
**输出**：`schema.ts`、变量结构注册脚本、状态栏 store 设计、世界书变量条目草案。  
**检查点**：
- [ ] 使用 Zod 4
- [ ] schema 具备幂等解析思路
- [ ] 动态集合优先使用 `record` 而非数组
- [ ] 需要默认值时优先 `prefault`
- [ ] `Schema.parse(Schema.parse(input))` 语义应稳定

### P0-2 MVU 初始化与最新楼层访问
**目标**：确保所有 MVU 逻辑都安全绑定到最新楼层。  
**输出**：统一的初始化时序与访问封装。  
**检查点**：
- [ ] 顶部先 `await waitGlobalInitialized('Mvu')`
- [ ] 在 `stat_data` 就绪前不开放读写
- [ ] 状态栏读写目标为 `message_id: 'latest'` 或 `-1`
- [ ] 不把状态栏绑定到旧楼层 `getCurrentMessageId()` 语义上

### P0-3 状态栏基础外壳
**目标**：落地状态栏基础 UI 与五大标签页壳。  
**输出**：脚本挂载的独立 iframe 状态栏，含属性/背包/卡牌/队友/任务入口。  
**检查点**：
- [ ] 使用脚本 + 独立 iframe 方案
- [ ] 初始化用 `$(() => {})`
- [ ] 销毁用 `pagehide`
- [ ] 如使用 Vue Router，则为 `createMemoryHistory()`
- [ ] 不依赖 DOMContentLoaded

### P0-4 聊天变量卡牌仓库
**目标**：实现冷数据仓库的增删查改。  
**输出**：卡牌仓库数据模型与基本管理能力。  
**检查点**：
- [ ] 仓库使用 `getVariables/replaceVariables({ type: 'chat' })`
- [ ] 正式卡牌不写入 MVU 全量热数据
- [ ] 删除操作有二次确认
- [ ] AI 无法直接写仓库

### P0-5 当前可见区与摘要复制
**目标**：完成从冷仓库到热摘要的过滤链路。  
**输出**：当前可见区管理、摘要复制、优先级机制。  
**检查点**：
- [ ] 只有摘要进入 MVU
- [ ] prompt 不扫描完整仓库
- [ ] 可见区与卡摘要分字段维护
- [ ] 超预算有提示策略

### P0-6 主聊天 AI 回写安全闭环
**目标**：保证 AI 更新只影响白名单内热数据。  
**输出**：解析、过滤、校验、回写链路。  
**检查点**：
- [ ] 自建 AI 请求后手动 `Mvu.parseMessage`
- [ ] 手动 `Mvu.replaceMvuData`
- [ ] 非法路径被拦截且提示用户
- [ ] HP/MP 不会写成负数
- [ ] 更新失败不静默

### P0-7 背包整理为正式卡牌
**目标**：实现“背包物品 -> 卡牌 JSON 草案 -> 仓库写入”的事务性流程。  
**输出**：整理入口、方向选择、AI 草案、校验与回滚。  
**检查点**：
- [ ] 先生成完整结果再提交
- [ ] 成功才消耗背包物品
- [ ] 失败整包回滚
- [ ] 稳定 `cardId` 生成规则已明确

### P0-8 DicePool / CombatLog 遮蔽
**目标**：阻断历史随机源与战斗记录污染上下文。  
**输出**：普通检定骰子池注入规则、历史遮蔽规则。  
**检查点**：
- [ ] 历史 `<DicePool>` 不发送给 AI
- [ ] 历史 `<CombatLog>` 不发送给 AI
- [ ] 普通检定走 one-shot 骰子池方案

### P0 验证顺序
- [ ] 最新楼层 MVU 可读写
- [ ] 状态栏壳正常显示
- [ ] 仓库与可见区联动正常
- [ ] AI 回写可过滤与校验
- [ ] 背包整理失败时能完整回滚
- [ ] 历史 DicePool/CombatLog 不污染上下文

## 4. P1 实施清单（战斗首版）

### P1-1 战斗浮窗外壳
**目标**：提供独立的战斗入口与隔离 UI。  
**检查点**：
- [ ] 使用脚本 + 独立 iframe
- [ ] 与状态栏生命周期互不冲突
- [ ] 关闭时能完整清理

### P1-2 战前快照与锁定机制
**目标**：让战斗可中止、可回滚。  
**检查点**：
- [ ] 进入战斗时保存最新楼层快照
- [ ] 锁定当前可见区修改
- [ ] 锁定仓库操作
- [ ] 锁定背包整理
- [ ] 放弃/关闭可恢复快照

### P1-3 战斗回合主流程
**目标**：建立“策略 -> 掷骰 -> 重掷 -> 确认 -> AI 推演 -> 回写”的闭环。  
**检查点**：
- [ ] 玩家先输入策略
- [ ] 前端/脚本负责投骰
- [ ] 每次战斗检定最多 3 次重 roll
- [ ] 先看骰面，再决定是否重掷
- [ ] 玩家确认后才把骰面发给 AI
- [ ] AI 负责数值推演和叙事

### P1-4 回合预览与确认写回
**目标**：在不依赖主聊天 one-shot 的前提下，稳定写回每回合结果。  
**检查点**：
- [ ] 支持回合预览
- [ ] 确认后才回写 MVU
- [ ] 自建 AI 请求必须手动 parse + replace
- [ ] 中间回合不向主楼层追加 CombatLog

### P1-5 战斗终局处理
**目标**：形成完整的结尾回写。  
**检查点**：
- [ ] 战斗结束后追加纯叙事 CombatLog
- [ ] 清空 `敌方`
- [ ] 覆盖 `世界.近期事务`
- [ ] 解锁状态栏相关操作

### P1-6 选做项：快速整场战斗
**目标**：在同样的确认机制下支持一次性整场推演。  
**检查点**：
- [ ] 不破坏回合制主流程
- [ ] 仍然支持终局回写规则

### P1 验证顺序
- [ ] 可从 `敌方` 进入战斗浮窗
- [ ] 战前快照可恢复
- [ ] 单次检定的掷骰/重掷/确认链路可用
- [ ] 玩家确认后 AI 才开始推演
- [ ] 战斗放弃可恢复战前状态
- [ ] 终局 CombatLog / 敌方清空 / 近期事务覆盖正确

## 5. P2 实施清单（高级扩展）

### P2-1 手动按钮触发的特殊判定
**目标**：先做最小风险版特殊检定。  
**检查点**：
- [ ] 支持高难度判定标签
- [ ] 支持多次暗骰
- [ ] 支持不可刷新
- [ ] 不影响普通战斗主流程

### P2-2 AI 结构化申请特殊判定
**目标**：允许 AI 在保留 GM 自由度的同时，受控地请求前端执行特殊检定。  
**检查点**：
- [ ] AI 只提交结构化请求，不直接操控脚本
- [ ] 请求格式可表达：次数、属性、DC、是否暗骰、是否可重掷
- [ ] 前端执行后将结果回传 AI

### P2 验证顺序
- [ ] 至少一种特殊判定可运行
- [ ] 不破坏 P1 公开投骰流程
- [ ] 暗骰与公开骰的 UI/状态区分清晰

---

## 6. 风险与优先规避项
1. **写错楼层**：状态栏误绑定旧楼层
2. **仓库泄漏**：完整卡牌内容进入 prompt
3. **半成功提交**：仓库未写入但背包已消耗
4. **MVU 未初始化即读写**
5. **战斗中途污染主楼层 CombatLog**
6. **直接使用低层接口导致生命周期/样式异常**
