> 基线来源：

## 1. 计划目标
将“旅法师卡牌 / 状态栏 / 战斗辅助系统”从需求规格推进到可实施的分阶段落地计划，覆盖：
- 任务拆解
- 依赖关系
- 阶段交付物
- 阶段验收标准
- 风险与验证策略

本计划不进入直接代码实现，仅作为执行前的正式 handoff 计划产物。

---

## 2. ADR（决策记录）

### Decision
采用 **P0 / P1 / P2 分阶段实施**：
- **P0**：数据层、状态栏、卡牌仓库、可见区、普通检定、主聊天安全回写
- **P1**：战斗浮窗、战前快照、投骰/重掷/确认、战斗回写闭环
- **P2**：特殊判定（多次暗骰、高难度隐藏检定、AI 结构化申请特殊判定）

### Drivers
1. 降低最早期实现失败风险
2. 先锁住冷热数据分层与 AI 回写安全
3. 适应 SillyTavern 主聊天 one-shot 限制
4. 保留 AI 的叙事与战斗推演自由度
5. 与 Tavern Helper / MVU 模板和 util 工具保持兼容

### Alternatives Considered
1. **首版一次性交付完整战斗系统**  
   - 否决原因：范围过大，容易在状态安全与战斗流程上同时失控
2. **脚本完整接管战斗数值结算**  
   - 否决原因：会显著削弱 AI 的自由推演能力，且复杂度高
3. **延续“系统自动判定普通检定”旧方案**  
   - 否决原因：与当前文档多数边界不一致，也不利于统一普通叙事裁定体验

### Why Chosen
当前方案在“最小稳定闭环”“战斗可玩性”“AI 自由度”之间平衡最好。

### Consequences
- P0 与 P1 需要严格分边界
- 实施期间必须优先建设回写安全、回滚与遮蔽机制
- 战斗将成为受控的前端子系统，而不是主聊天一次性结算文本

---

## 3. 计划原则
1. **先安全，后扩展**：先做数据与回写安全，再做高交互战斗
2. **先工具兼容，后抽象优化**：优先复用 `util/*` 与角色卡模板
3. **先公开投骰，再特殊判定**：P1 不引入复杂暗骰机制
4. **所有关键流程都必须可回滚或拒绝提交**
5. **不让 AI 直接写受保护的长期结构**

---

## 4. 阶段概览

| 阶段 | 目标 | 主要交付物 | 是否依赖前序 | 风险等级 |
|---|---|---|---|---|
| P0 | 建立最小稳定闭环 | MVU schema、状态栏壳、仓库、可见区、回写安全、背包整理 | 无 | 中 |
| P1 | 建立战斗首版闭环 | 战斗浮窗、战前快照、投骰/重掷/确认、终局回写 | 依赖 P0 | 高 |
| P2 | 扩展高级 GM 判定能力 | 特殊判定、暗骰、多段检定、AI 结构化申请 | 依赖 P1 | 中高 |

## 5. 工作分解结构（WBS）

## P0：最小稳定闭环

### P0-W1：MVU 变量结构与注册
**任务**
- P0-W1-T1 定义 `schema.ts`：世界、化身、背包、任务、队伍、当前状态、当前可见区、当前可见卡摘要、敌方
- P0-W1-T2 为动态集合使用 `z.record` 结构
- P0-W1-T3 为关键数值设计 clamp / transform / prefault 规则
- P0-W1-T4 编写变量结构注册脚本（最小职责，仅注册 `Schema`）
- P0-W1-T5 形成世界书变量条目清单：initvar / 变量列表 / 更新规则 / 输出格式

**依赖**
- 无

**交付物**
- `schema.ts` 设计方案
- 变量结构注册脚本方案
- 世界书变量条目草案

**验收标准**
- schema 可表达全部 P0 热状态
- 幂等解析思路明确
- old/new diff 相关约束未误塞入 schema

---

### P0-W2：最新楼层 MVU 访问与状态栏架构
**任务**
- P0-W2-T1 定义状态栏采用“脚本 + 独立 iframe”方案
- P0-W2-T2 设计 latest/-1 语义的 store 访问方式
- P0-W2-T3 明确等待时序：`waitGlobalInitialized('Mvu')` -> `stat_data` ready -> mount
- P0-W2-T4 设计状态栏五大标签页壳
- P0-W2-T5 明确初始化/销毁生命周期：`$(() => {})` / `pagehide`

**依赖**
- 依赖 P0-W1 输出的 schema 结构

**交付物**
- 状态栏架构说明
- latest store 访问方案
- 生命周期方案

**验收标准**
- 状态栏永远读写最新楼层，而非旧楼层
- 模板示例中的 `getCurrentMessageId()` 风险已被规避
- 方案显式使用 `createScriptIdIframe()` 作为推荐挂载原语

---

### P0-W3：聊天变量卡牌仓库与当前可见区
**任务**
- P0-W3-T1 设计正式卡牌仓库结构（聊天变量）
- P0-W3-T2 设计当前可见区字段与摘要字段（MVU 热数据）
- P0-W3-T3 定义仓库 -> 摘要复制规则
- P0-W3-T4 定义可见区优先级与超预算提示策略
- P0-W3-T5 定义删除卡牌后的引用清理规则

**依赖**
- 依赖 P0-W1 schema
- 与 P0-W2 状态栏显示联动

**交付物**
- 仓库字段说明
- 当前可见区规则
- 摘要复制规则

**验收标准**
- 完整仓库不会默认进入 prompt
- 当前可见卡摘要可以独立热更新
- 删除卡牌后的引用处理规则明确且无悬空引用

---

### P0-W4：主聊天 AI 回写安全链路
**任务**
- P0-W4-T1 定义允许更新的白名单路径
- P0-W4-T2 定义非法更新的提示与拒绝策略
- P0-W4-T3 设计主聊天自建 AI 请求后的 `parse -> filter -> validate -> replace` 链路
- P0-W4-T4 明确 HP/MP 非负保护与数值边界保护
- P0-W4-T5 定义普通检定骰子池注入与历史 `<DicePool>` / `<CombatLog>` 遮蔽规则

**依赖**
- 依赖 P0-W1 schema
- 依赖 P0-W2 的 MVU 访问稳定性

**交付物**
- 回写链路设计
- 白名单规则表
- 骰子池与历史遮蔽策略

**验收标准**
- 自建 AI 请求不会自动写 MVU，必须手动 parse/replace
- 非法路径不静默失败
- 历史 DicePool / CombatLog 不进入后续上下文

---

### P0-W5：背包整理为正式卡牌的事务性流程
**任务**
- P0-W5-T1 定义整理入口与方向枚举
- P0-W5-T2 定义 AI 生成卡牌 JSON 草案的输入与输出形状
- P0-W5-T3 设计 Zod 清洗与稳定 `cardId` 生成方案
- P0-W5-T4 设计“成功才消耗、失败整包回滚”的事务流程
- P0-W5-T5 定义用户提示与错误展示

**依赖**
- 依赖 P0-W1 schema
- 依赖 P0-W3 仓库结构
- 依赖 P0-W4 回写安全链路

**交付物**
- 卡牌整理流程图
- JSON 草案格式
- 回滚规则

**验收标准**
- 不出现半成功状态
- 稳定 cardId 规则明确
- 用户能理解失败原因

### P1-W3：单次战斗检定的交互闭环

## 8. 风险清单与缓解

| 风险 | 所在阶段 | 影响 | 缓解 |
|---|---|---|---|
| 状态栏误绑定旧楼层 | P0 | 数据错写 | 强制 latest/-1 语义；禁止直接照搬 `getCurrentMessageId()` store |
| 完整仓库泄漏进 prompt | P0 | 上下文膨胀/设定污染 | 仓库与摘要字段分离；仅摘要进入热状态 |
| 背包整理半成功 | P0 | 数据损坏 | 事务式提交；失败整包回滚 |
| MVU 未初始化就读写 | P0 | 界面异常/写入失败 | `waitGlobalInitialized('Mvu')` + `waitUntil(stat_data ready)` |
| 战斗中间回合污染主楼层 | P1 | 聊天混乱 | CombatLog 仅终局写入 |
| 脚本试图完整结算战斗 | P1 | 复杂度爆炸 | 明确 AI 负责数值推演，脚本只控流程 |
| 特殊判定过早引入 | P1/P2 | 主流程不稳 | 特殊判定严格延后到 P2 |

## 10. 阶段退出标准（Exit Criteria）

### P0 Exit
- 所有热数据读写与回写安全链路稳定
- 关键事务流程无半成功状态
- 状态栏可以稳定承载后续 P1 依赖

### P1 Exit
- 战斗可完整开始、进行、放弃、结束
- 玩家确认骰面后 AI 才推演
- 战斗结束后的主楼层回写规则无歧义

### P2 Exit
- 特殊判定机制可选启用
- 不破坏 P1 基础战斗体验
- AI 的 GM 式自由裁量通过结构化边界被约束

---

## 11. 推荐执行顺序
1. 先实现 / 冻结 P0-W1
2. 再实现 P0-W2 与 P0-W4
3. 然后完成 P0-W3 与 P0-W5
4. P0 验收通过后再进入 P1
5. P1 只做公开投骰战斗首版，不提前引入特殊判定
6. P2 最后做 GM 式高级机制
