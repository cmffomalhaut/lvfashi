## 二、状态机核心（session.ts）

### 2.1 生命周期

```
┌──────────────┐
│     idle     │  ← 初始态/战斗结束态
└──────┬───────┘
       │ startBattle()
       ▼
┌──────────────┐
│ player_input │  ← 玩家填写策略 + 明骰
└──────┬───────┘
       │ confirmPlayerCheck()
       ▼
┌──────────────┐
│  ai_resolve  │  ← AI 结算中（可能卡住）
└──────┬───────┘
       │ resolveConfirmedRound() → AI 返回 preview
       ▼
┌──────────────┐
│   preview    │  ← 等待玩家确认预览
└──────┬───────┘
       │ applyPendingPreview()
       ↓ player_input (下一回合)
       │ finishBattle()
       ▼
┌──────────────┐
│  finished    │  ← 战斗结束态
└──────┬───────┘
       │ commitBattle()  → 写回主状态，清空 battle_session
       │ abandonBattle() → 恢复战前快照，清空 battle_session
       ▼
┌──────────────┐
│     idle     │
└──────────────┘
```

### 2.2 关键函数

| 函数 | 位置 | 作用 | 事务边界 |
|------|------|------|----------|
| `startBattle()` | session.ts L210 | 从主状态构建 battle_session，保存快照，初始化 player_check 和暗骰池 | editCanonicalState(scope:battle_session) |
| `resumeOrRebuild()` | L222 | 检查现有 battle_session，不一致则回滚到 checkpoint | editBattleSession |
| `setStrategyText()` | L251 | 写入玩家策略 | editBattleSession |
| `rerollPlayerCheck()` | L264 | 重掷明骰（rollD20 + reroll_used+1） | editBattleSession |
| `confirmPlayerCheck()` | L323 | 锁定 player_check → ai_resolve → 调 AI 结算 | editBattleSession + resolveConfirmedRound |
| `resolveConfirmedRound()` | L292 | 调 resolve.ts → 写入 pending_preview → phase=preview | editBattleSession |
| `mockPreview()` | L340 | 本地假 preview（不调 AI） | editBattleSession |
| `applyPendingPreview()` | L353 | 应用 preview 到下一回合（combatants 更新 + 回合+1 + 阵营轮换 + 重置检定） | editBattleSession |
| `finishBattle()` | L377 | phase → finished，保留最终 checkpoint | editBattleSession |
| `commitBattle()` | L467 ➔ commit.ts | 终局写回主状态（主角化身、队伍、敌方清空、背包合并、近期事务追加） | editCanonicalState(scope:battle_session) |
| `abandonBattle()` | L469 | 恢复 prebattle_snapshot 到主状态，清空 battle_session | editCanonicalState |
| `appendRuntimeChatMessage()` | L391 | 追加 runtime transcript 条目 | editBattleSession |

### 2.3 两种流程

**经典流程（无 battle profile / no-UI 模式）：**
1. `startBattle()` → 构建 battle_session
2. `setStrategyText()` → 写入策略
3. `confirmPlayerCheck()` → 锁定 → phase=ai_resolve → resolveConfirmedRound() → 调 resolve.ts AI → 写入 preview → phase=preview
4. `applyPendingPreview()` → 应用预览 → phase=player_input（下一回合）
5. ... 循环直到 `finishBattle()` → phase=finished
6. `commitBattle()` → 写回主状态

**Runtime 流程（有 battle profile / UI 模式）：**
1. `store.executeConfiguredBattleTurn()` → 调 `runtime-ai.ts` 的 `requestBattleSingleRound()`
2. → 调 `runtime-session.ts` 的 `createPendingPreviewFromRoundResult()` 构建 preview
3. → 调 `applyRuntimeRoundPreview()` 写入 session
4. 类似地有 `executeConfiguredLootResolution()` / `applyRuntimeLootResult()`

### 2.4 事务隔离设计

- `editCanonicalState`: 读写完整 canonical state（写 scope 可选 full 或 battle_session_only）
- `editMainState`: 只读写 MainState，postCheck 确保 battle_session 不变
- `editBattleSession`: 只读写 battle_session，postCheck 确保 MainState 投影不变

这三层是强制事务隔离，不可绕过。

### 2.5 Round Checkpoint 机制

`captureRoundCheckpoint()` 在每个 player_input 起点保存全量副本。
`restoreRoundCheckpoint()` 回滚到上一个 checkpoint。
`hasUncommittedRoundState()` 检测是否有未提交的变更。

这和 step-by-step undo 类似，任何未 commit 的回合变更都可以被 `resumeOrRebuild()` 回滚。

## 三、骰子系统全流程分析

### 3.1 数据结构

```typescript
// session.ts
const rollD20 = () => _.random(1, 20);     // 1–20 随机
const darkPool = () => Array.from({ length: 5 }, () => rollD20());

function createFreshPlayerCheck() {
  return PlayerCheckSchema.parse({
    strategy_text: '',
    roll: 0,             // 未投骰状态；首次投骰由 rerollPlayerCheck() 写入
    reroll_used: 0,
    confirmed: false,
  });
}
```

### 3.2 服务端（session.ts）骰子操作

| 函数 | 操作 |
|------|------|
| `createFreshPlayerCheck()` | 创建新检定：roll = 0 |
| `rerollPlayerCheck()` | 投骰/重掷：roll = rollD20()；已有 roll 时 reroll_used += 1，首次投骰仍为 0；重投上限 99 |
| `confirmPlayerCheck()` | 锁定：confirmed = true |
| `buildBattleSession()` | 开战时创建 player_check + shared_dark_pool |
| `applyPendingPreview()` | 下一回合时重置：`player_check = createFreshPlayerCheck()`, `shared_dark_pool = darkPool()` |
| `applyRuntimeRoundPreview()` | 同上一行 |

### 3.3 UI 层（App.vue）骰子相关

```typescript
// reactive state
const lastDiceMessage = ref('');                                // 本地骰子消息
const lastDicePlayerCheck = ref<{roll, reroll_used, confirmed} | null>(null);  // 本地缓存
const diceDialogOpen = ref(false);
const diceAnimating = ref(false);

// computed
const effectiveDiceCheck = computed(() => {
  if (lastDicePlayerCheck.value?.roll && lastDicePlayerCheck.value.roll > 0)
    return lastDicePlayerCheck.value;                           // 优先本地
  if (battleSession.value.激活 && battleSession.value.player_check.roll > 0)
    return battleSession.value.player_check;                    // 其次 session
  return null;
});

const canOpenDiceDialog = computed(() =>
  !isFreeformRuntime && !isResolving && !isRuntimeRequestBusy
  && (!effectiveDiceCheck.value || !effectiveDiceCheck.value.confirmed)
);
const canRollDice = computed(() =>
  !isResolving && !isRuntimeRequestBusy
  && (!effectiveDiceCheck.value
    || (!effectiveDiceCheck.value.confirmed
      && (effectiveDiceCheck.value.roll <= 0 || effectiveDiceCheck.value.reroll_used < 99)))
);

// watch: 同步 session player_check 到本地
watch(() => battleSession.value.player_check, value => {
  if (battleSession.value.激活) {
    lastDicePlayerCheck.value = { roll: value.roll, reroll_used: value.reroll_used, confirmed: value.confirmed };
    return;
  }
  lastDicePlayerCheck.value = null;
}, { immediate: true });

// 本地骰子操作
const rollLocalDice = () => {
  const current = lastDicePlayerCheck.value;
  lastDicePlayerCheck.value = {
    roll: _.random(1, 20),
    reroll_used: current ? current.reroll_used + 1 : 0,
    confirmed: false,
  };
};

const reroll = async () => {
  if (battleSession.value.激活) {
    const result = await store.reroll();
    syncLastDiceCheckFromResult(result);
  } else {
    rollLocalDice();
  }
  showDiceDialog(true);
};

const acceptDiceDialog = async () => {
  if ((effectiveDiceCheck.value?.roll ?? 0) <= 0) {
    if (battleSession.value.激活) {
      const result = await store.reroll();
      syncLastDiceCheckFromResult(result);
    } else {
      rollLocalDice();
    }
  }
  lastDiceMessage.value = `技能：1d20=${diceRollLabel.value}`;
  diceDialogOpen.value = false;
  if (battleSession.value.激活) {
    store.appendRuntimeChatMessage({ role: 'system', label: '骰子', content: lastDiceMessage.value });
  }
};

// 填充到 AI 请求的 diceInputs
const buildBattleCommandOptions = () => ({
  diceInputs: battleSession.value.激活 ? {} : {
    player_roll: effectiveDiceCheck.value?.roll || undefined,   // 取本地值
    reroll_used: effectiveDiceCheck.value?.reroll_used ?? 0,
    dark_pool_remaining: Array.from({ length: 5 }, () => _.random(1, 20)), // 仅无 session 测试请求使用
    dark_pool_cursor: 0,
  }
});
```

## 五、AI 结算系统

### 5.1 resolve.ts（基础版本）

```typescript
buildBattleResolveSystemPrompt() → 7 条规则
  "你是旅法师战斗回合裁定器"
  "只返回本回合预览草案"
  "必须保留原有单位 id"
  "没有明确掉落时 proposed_loot 返回空对象"
  ...

→ generateRaw({ json_schema: BATTLE_PREVIEW_JSON_SCHEMA, ordered_prompts: [system, user_with_promptPayload] })
→ 返回 PendingPreview
```

JSON Schema 强制输出：summary, proposed_world_events, proposed_combatants, proposed_loot

### 5.2 runtime-ai.ts（profile 版本）

四套独立 prompt（字段分析/单回合/整场/战利品），各自有 system/user/output contract prompt。
AI 调用的方式：
- `requestBattleSingleRound()` → `requestRuntimeJson()` → `requestBattleChatCompletion()` → axios POST /chat/completions
- 重试机制：指数退避 500ms × 2^n，可配置 retry_limit

三个 payload builder：
- `buildBattleRuntimePayload()` → selected_data + player_command + dice_inputs + worldbook_context + environment_context + extra_instructions
- `buildBattleLootPayload()` → 同上但 task=resolve_loot

三大数据验证 schema（Zod）：
- `BattleRoundResultSchema`：解析 round 结果（含 `round_index`, `summary`, `narration`, `selected_data_updates`, `status_changes`...）
- `BattleFullResultSchema`：解析整场结果（含 `rounds[]`, `final_selected_data_updates`, `battle_report`...）
- `BattleLootResultSchema`：解析战利品结果（含 `loot_result`, `mvu_updates`...）

状态机适配器在 `runtime-ai.ts` 内部 `normalizeBattleStateValue()` 处理中文/英文变体 → 'ongoing' | 'finished'。

### 5.3 runtime-session.ts（preview 构建）

```
createPendingPreviewFromRoundResult(session, roundResult)
  → mergeBattleRuntimeUpdates(accumulated_updates, selected_data_updates)
  → buildRuntimeMainState(session, accumulated_updates)
  → PendingPreview: { summary, proposed_world_events, proposed_combatants, proposed_loot }

createPendingPreviewFromFullBattleResult(session, fullResult)
  → 同上但用 final_selected_data_updates
  → proposed_world_events 包含全部回合的 digest

createPendingPreviewFromLootResult(session, lootResult)
  → 合并 mvu_updates + loot_result 到 preview
```

`projectMainStateFromBattleSession()`：把 battle_session 投影为 MainState（从 prebattle_snapshot + combatants 拼合）

`buildRuntimeMainState()`：在投影基础上施加 accumulated_updates。

## 六、字段树系统（field-selection.ts + field-analysis.ts）

### 6.1 字段树构建

`buildBattleFieldTree(statData)` → 递归遍历所有键值：
- scalar 显示值（最长 60 字符）
- object 显示子级数
- array 显示长度
- 中文排序

### 6.2 字段选择

- `selected_fields: BattleSelectedField[]` 持久化在 battle profile 中
- 每个 field 含 path, label, enabled, source('ai'|'manual'), reason, value_kind
- 祖先/后代关系处理：
  - `isSameOrAncestorPath()` 判断一个路径是否包含另一个
  - `hasIncludedBattleFieldAncestor()` 检测是否有已选择的祖先（用于显示"排除子级"操作）
- `extractSelectedBattleData()` 从 stat_data 中提取被选字段的数据

### 6.3 AI 字段分析

`analyzeBattleFields()` → 调 AI 推荐需要观察的字段路径 → 解析为 `BattleFieldSelectionConfig`
结果写入 battle profile 的 `field_selection`，设置 `manual_review_required: true`，等待玩家确认。

### 6.4 hash 机制

- `buildBattleFieldSelectionSourceHash()`: FNV-1a hash of stat_data 结构签名 → 用于检测数据变化
- `createAnalysisInputHash()`: djb2 hash of (run_mode + battle_protocol + stat_data + ...) → 用于检测是否需要重新分析

## 七、MVU 更新系统（battle-updates.ts）

### 7.1 路径命名空间

AI 返回的更新路径必须前缀 `stat_data.`，否则拒绝。
路径校验阻止 `__proto__`, `prototype`, `constructor`。

```typescript
// AI 返回的示例
{ "stat_data.主角.当前化身.状态效果": [...], "stat_data.世界.近期事务.battle_1": "..." }
```

### 7.2 合并策略

- `mergeBattleRuntimeUpdates(baseUpdates, nextUpdates)`:
  - 每个回合的 selected_data_updates 累加到 accumulated_updates
  - 对象深度合并（不是直接覆盖），标量直接覆盖
- `applyBattleRuntimeUpdates(state, updates)`: 把 updates 写到 state 副本
  - 路径自动尝试 `角色数据.{path}` 作为 fallback

### 7.3 事务写入

`writeBattleFlatUpdatesToMainState()` → 用 `editMainState` 事务直接写到主状态。

## 十三、已知设计缺陷汇总

### 13.1 核心缺陷

1. **prompt.ts 的数据源不一致**：`buildNormalPromptPayload` 从 mainState 取数据，`buildBattleRoundPrompt` 从 `session.prebattle_snapshot` + `combatants` 取——两者路径/结构可能不同步
2. **经典流程 vs Runtime 流程双轨制**：`confirm()` 按有没有 `battleProfileDraft` 走完全不同的路径（一个走 session.ts 的 confirmPlayerCheck→resolve.ts，另一个走 store.ts 的 executeConfiguredBattleTurn→runtime-ai.ts）

### 13.1.1 本轮已修复

1. **骰子 UI 与 Session 不同步**：活跃战斗中的投骰/重投已改为调用 `store.reroll()`，写入 `battle_session.player_check`。
2. **活跃战斗暗骰池 UI 侧伪造**：`buildBattleCommandOptions()` 在 battle_session 激活时不再传本地 `diceInputs`，正式 runtime 请求由 store 从 `session.shared_dark_pool` 读取。无 battle_session 的测试请求仍会生成本地临时暗骰。

### 13.2 架构复杂度

- UI 层（App.vue）直接依赖了 session 层、store 层、field-selection 层、runtime-ai 层——职责边界模糊
- `lastDicePlayerCheck` 和 `lastDiceMessage` 作为本地缓存与 session 数据存在两份副本，同步规则复杂且容易出 bug
- 经典流程（无 profile）和 Runtime 流程（有 profile）对骰子的处理方式完全不同
