## 功能一：战斗对话写入主聊天

> 实现状态：✅ **已完成**  
> 实现文件：`commit.ts` — `buildOutputMessage()` + `commitBattleOutcome()` 中的入楼逻辑  
> 触发入口：`App.vue` 的「确认入楼」按钮 → `store.commitBattle()` → `session.commitBattle()` → `commitBattleOutcome()`

### 核心原则

- **只发生在战斗结束时**，不是在每回合结束后逐楼发送
- **一次性打包**所有回合内容后写入，不是逐回合 append
- `commitBattle()` 后写入楼层，时间点在 `editCanonicalState()` 成功之后
- 写入的楼层应插入到当前消息的末尾（`createChatMessages` 默认 `insert_before: 'end'`）
- **数据源是 `runtime.history`，不是 `runtime.transcript`**。AI 返回的 `narration` 已经包含了骰子结果、双方行动、AI 叙述的全部内容，不需要用 transcript 重复玩家和骰子日志。

### 完整模式（`output_to_chat_mode = 'full'`）

**输出内容**：将 `runtime.history` 中每回合的 `narration` 合并在一起，作为 **1 条** `assistant` 消息。

**数据源**：`battle_session.runtime.history[].narration`

```typescript
// schema 定义 (schema.ts L244-249)
history: z.array(z.object({
  round_no: z.number().prefault(0),
  type: z.enum(['round', 'full_battle', 'loot']).prefault('round'),
  summary: trimmedString().prefault(''),
  narration: trimmedString().prefault(''),   // ← AI 返回的完整回合叙述
})).prefault([]),
```

**生成示例**：
```
// history 数组：
[
  { round_no: 1, narration: '你挥剑斩向首领，剑光划破黑暗。首领发出一声怒吼，挥爪反击，你侧身躲过。', ... },
  { round_no: 2, narration: '队友趁机发动夹击，箭矢如雨。首领身上多了数道伤口，动作开始迟缓。', ... },
  { round_no: 3, narration: '你凝聚力量发动致命一击，首领轰然倒地。战斗结束，你方获胜。', ... },
]

// 写入楼层（1层 assistant）：
// [assistant]
// 你挥剑斩向首领，剑光划破黑暗。首领发出一声怒吼，挥爪反击，你侧身躲过。
// 队友趁机发动夹击，箭矢如雨。首领身上多了数道伤口，动作开始迟缓。
// 你凝聚力量发动致命一击，首领轰然倒地。战斗结束，你方获胜。
```

### 摘要模式（`output_to_chat_mode = 'summary'`）

**输出内容**：将 `runtime.history` 中每回合的 `summary` 合并在一起，作为 **1 条** `assistant` 消息。

**数据源**：`battle_session.runtime.history[].summary`

```typescript
history: z.array(z.object({
  round_no: z.number().prefault(0),
  type: z.enum(['round', 'full_battle', 'loot']).prefault('round'),
  summary: trimmedString().prefault(''),    // ← AI 返回的回合摘要
  narration: trimmedString().prefault(''),
})).prefault([]),
```

**生成示例**：
```
// history 数组：
[
  { round_no: 1, summary: '你成功吸引了首领注意，但受到轻微伤害', ... },
  { round_no: 2, summary: '队友趁机输出，首领血量过半', ... },
  { round_no: 3, summary: '首领狂暴，你方被迫后撤', ... },
]

// 写入楼层（1层 assistant）：
// [assistant]
// 第1回合：你成功吸引了首领注意，但受到轻微伤害
// 第2回合：队友趁机输出，首领血量过半
// 第3回合：首领狂暴，你方被迫后撤
// 战斗结束，我方获胜。
```

### 两种模式的共同特征

| | 完整模式 | 摘要模式 |
|--|---------|---------|
| 写入层数 | **1 条** assistant | **1 条** assistant |
| 数据源 | `history[].narration` 合并 | `history[].summary` 合并 |
| 是否含骰子日志 | 包含（AI 叙述已内嵌） | 不包含 |
| 是否含玩家策略 | 包含（AI 叙述已内嵌） | 不包含 |
| 目标 | 沉浸式阅读完整战况 | 快速了解战斗走向 |

### 触发时机与钩子位置（实现记录）

**入口点**：`commit.ts` → `commitBattleOutcome()` → `editCanonicalState` 成功后

**已实现方式**：**方案 1**（`commit.ts` 内直接入楼）

```typescript
// commit.ts L103-L171 — commitBattleOutcome()
export async function commitBattleOutcome(access, { sourceMessageId, summary, fullLog, outputMode }) {
  // 1. 在 mutate 闭包外捕获快照和模式
  let historySnapshot = [];
  let resolvedOutputMode = 'summary_only';

  const result = await access.editCanonicalState({
    sourceMessageId,
    mutate: draft => {
      // 2. 在清空 session 之前捕获历史快照
      historySnapshot = klona(session.runtime.history);
      resolvedOutputMode = outputMode ?? session.output_mode;
      // ... MVU 更新、战场结算 ...
      draft.battle_session = BattleSessionSchema.parse({}, { reportInput: true });
    },
    // ...
  });

  // 3. editCanonicalState 成功后，用快照数据入楼
  if (result.ok && historySnapshot.length > 0) {
    try {
      const message = buildOutputMessage(historySnapshot, resolvedOutputMode);
      if (message.trim()) {
        await createChatMessages([{ role: 'assistant', message }], { refresh: 'all' });
      }
    } catch (e) {
      console.error('[Battle] Failed to output battle dialog to chat:', e);
    }
  }

  return result;
}
```

**关键实现细节**：

- `historySnapshot` 在 `mutate` 闭包内捕获，此时 `session.runtime.history` 还未被清空
- `resolvedOutputMode` 也同时捕获，决定用 `summary_only`（合并 summary）还是 `full_log`（合并 narration）
- 入楼失败（`try/catch`）**不影响 commit 本身**，只是 console.error
- 入楼数据在 `editCanonicalState` **成功之后**写入，确保状态一致性
- 使用 `klona()` 深拷贝快照，避免后续闭包内 session 清空后引用失效

### 插入位置

- 战斗窗口本身是一个**独立 iframe**，不是嵌入在聊天楼层中
- 战斗相关的 MVU 数据存储在**源消息楼层**（即打开战斗窗口时所在楼层）的 `data.stat_data` 中
- 但写入楼层时应插入到**最新消息之后**（chat 末尾），而不是源消息楼层附近
- 使用 `createChatMessages([message], { insert_before: 'end', refresh: 'all' })`

## 功能四：JSON 解析健壮性

> 实现状态：✅ **已完成**  
> 实现文件：`runtime-ai.ts` — `parseRuntimeStructuredText()` + `requestRuntimeJson()` 中的兜底逻辑

### 背景

在 Runtime/Profile 流程中，AI 返回的 JSON 需要经过两道关卡：

1. **`parseRuntimeStructuredText()`** — 从 AI 返回的文本中解析出 JSON 对象
2. **`BattleRoundResultSchema.parse()`** — 用 Zod 校验和标准化解析后的对象

实际运行时发现了两个断裂点：

- **断裂点 A**：AI 返回的文本含有 BOM 头、前导文本或格式异常 → `parseRuntimeStructuredText` 直接抛出异常，流程中断
- **断裂点 B**：AI 返回的 JSON 合法，`parseRuntimeStructuredText` 正确解析，但 `BattleRoundResultSchema.parse()` 输出所有 `.prefault()` 默认值（`summary=""`, `narration=""`, `round_index=0` 等），真实内容丢失

断裂点 B 的根因推测是 Zod v4 中 `preprocess` + `.prefault()` 的交互问题，或中间某个 `normalize` 函数丢弃了数据。

### 三层兜底机制

#### 第 1 层：`parseRuntimeStructuredText` 抛异常时（`runtime-ai.ts L167-L201`）

```typescript
// 如果 JSON 解析失败，不抛出异常而是构建合成对象
// 找出第一个 { } 包围的 JSON 对象，提取原始文本
const rawMatch = rawText.match(/\{[\s\S]*\}/);
if (rawMatch) {
  return {
    result_type: 'round',
    battle_state: 'ongoing',
    narration: rawText.trim(),
    // ... 其他默认字段
  };
}
```

**触发条件**：AI 返回的不是合法 JSON（有 BOM、前导描述文字等）

**结果**：返回合成对象，原始文本作为 `narration`，后续依赖此字段输出

#### 第 2 层：`requestRuntimeJson` 的 Zod 解析结果为空时（`runtime-ai.ts L627-L720`）

```typescript
// 在标准解析路径末尾，检查 Zod 输出是否为空
const parsed = BattleRoundResultSchema.parse(extracted);

// 如果 parsed 的内容字段为空但 rawText 有实质内容 → 兜底
if (isBattleRoundResultEmpty(parsed) && isRawTextNonEmptyNoise(rawText)) {
  return buildFallbackRoundResult(rawText);
}
```

**触发条件**：JSON 合法 + 解析成功 + 但 Zod 产出的所有内容字段为空

**结果**：用 `isBattleRoundResultEmpty()` 检测空结果，`isRawTextNonEmptyNoise()` 过滤纯 `{}` / `[]` 噪音，然后 `buildFallbackRoundResult()` 构建兜底对象

#### 第 3 层：重试路径同样检查

当 `allow_retry_on_invalid_json = true` 且重试成功后，同样走第 2 层的检查逻辑。

## 功能二：历史上下文注入

### 用途

在构建战斗 prompt 时，从主聊天中读取战斗开始前的最近几楼消息，作为上下文注入给 AI，让 AI 了解当前剧情语境。

### 数据源

`getChatMessages(range, options)` — 从主聊天读取历史楼层。

### 推荐实现方式

在 `prompt.ts` / `runtime-ai.ts` 中新增一个上下文收集步骤：

```typescript
// 读取最近 N 条用户/AI 消息（不含 system）
const recentMessages = getChatMessages(`-${RECENT_COUNT}`, {
  role: 'all',
  hide_state: 'unhidden',
});
// RECENT_COUNT 建议为 3-5 条
```

### 关键参数

| 参数 | 值 | 说明 |
|------|-----|------|
| `range` | `'-5'` | 负数表示从末尾向前取，-5 表示最近 5 楼 |
| `role` | `'all'` | 获取所有角色的消息（user + assistant） |
| `hide_state` | `'unhidden'` | 不要已隐藏的楼层 |
| `include_swipes` | 默认 `false` | 只取被 AI 使用的消息页 |

### 集成到 prompt 的位置

- **已有字段**：`BattleContextConfig` 中的 `include_floor_context`（`ai-profile.ts L117`）
- 当 `include_floor_context === true` 时，在 `runtime-payload` 或 `buildBattleRoundPrompt` 中加入最近楼层内容
- 需要新增 **开关配置** 和 **消息数量配置**

### 新增配置字段建议

在 `BattleContextConfig` 中新增：

```typescript
// ai-profile.ts BattleContextConfig
export type BattleContextConfig = {
  include_worldbook_context: boolean;
  include_environment_context: boolean;
  include_floor_context: boolean;       // ← 已有，但未实现
  include_recent_battle_report: boolean;
  worldbook_max_chars: number;
  imported_worldbooks: BattleImportedWorldbook[];
  extra_context_text: string;
  // 建议新增：
  recent_floor_count: number;           // 读取最近几楼，默认 3
  recent_floor_max_chars: number;       // 截断字符数，默认 1500
};
```

## 功能三：标签过滤

### 用途

在构建上下文注入时，根据楼层标签（`tag`）筛选或排除特定楼层。例如：
- 只注入包含 `"战斗"` 标签的楼层
- 排除 `"OOC"` 标签的楼层
- 排除 `"系统"` 标签的楼层

### 技术限制

酒馆原生的 `getChatMessages()` 返回的 `ChatMessage` 类型中**没有直接的 `tag` 字段**：

```typescript
type ChatMessage = {
  message_id: number;
  name: string;
  role: 'system' | 'assistant' | 'user';
  is_hidden: boolean;
  message: string;
  data: Record<string, any>;    // ← 楼层变量/自定义数据存放在这里
  extra: Record<string, any>;   // ← 扩展数据
};
```

### 实现方式

**方式 A：通过 `data` 中的自定义字段**
- 如果楼层使用了 MVU 变量或自定义 `data` 字段，可以通过 `data.tag` 或类似字段筛选
- 示例：`chatMessages.filter(m => m.data?.tag !== 'OOC')`

**方式 B：通过 `extra` 扩展数据**
- 某些酒馆插件或扩展会在 `extra` 中写入标签信息
- 但 `extra` 字段的内容取决于扩展实现，不保证存在

**方式 C：文本关键词匹配（推荐）**
- 在获取最近 N 楼后，用正则/关键词匹配 `message` 文本
- 例如：如果消息包含 `【OOC】` 前缀，则跳过
- 不需要依赖楼层元数据，鲁棒性高

### 新增配置字段建议

在 `BattleContextConfig` 中新增：

```typescript
export type BattleContextConfig = {
  // ... 现有字段
  // 建议新增：
  filter_exclude_keywords: string[];    // 排除包含关键词的楼层
  filter_include_keywords: string[];    // 只保留包含关键词的楼层（为空则不筛选）
};
```

## 未来展望：正则导入与管理

### 背景

战斗内容入楼后，如果能配合专门的正则规则（如骰子高亮、战斗日志格式化等），显示效果会更好。用户可能希望导入自己收集的战斗正则文件，或在不需要时删除。

### 导入正则

**可行性**：技术上完全可行，难度中低。

酒馆正则 API 提供了完整的读写能力：

```typescript
// 读取当前正则
const regexes = getTavernRegexes({ type: 'global' });

// 完全替换正则列表
await replaceTavernRegexes(newRegexes, { type: 'global' });
```

**导入流程**：
```
用户选择 .json 文件（酒馆导出的正则格式）
  → 解析 JSON → TavernRegex[]
  → 追加/替换到现有正则列表
  → replaceTavernRegexes()
```

**需要决策的点**：
- 合并策略：追加到末尾？按 `script_name` 去重替换？
- 数量大时：`replaceTavernRegexes` 会触发 `CHAT_CHANGED` 事件重载所有楼层，可能卡顿

### 删除正则

**需要区分来源**：否则删除时会误删用户原有的正则。

**推荐做法**：导入时给正则的 `script_name` 加前缀标记，如 `[Battle] 骰子高亮`。删除时按前缀匹配过滤：

```typescript
const BATTLE_REGEX_PREFIX = '[Battle]';

await updateTavernRegexesWith(regexes => {
  return regexes.filter(r => !r.script_name.startsWith(BATTLE_REGEX_PREFIX));
}, { type: 'global' });
```

### 正则美化（`formatAsTavernRegexedString`）

写入前对文本预处理应用正则也是一个可选方向。如果选择做，**推荐方案 A**：

> **写入原始文本，让酒馆在显示时自行应用正则。**

理由：
- 酒馆显示楼层时本来就会应用正则 → 预处理会导致**双重应用**
- 写入原始文本 = 最少侵入 + 最少出错
- 用户调整正则后，历史楼层的显示也会自动跟随变化

### 定位

正则导入/删除是战斗系统的**周边辅助功能**，不是核心战斗流程。建议在入楼和上下文注入两个核心功能落地后再考虑。

## 注意事项

### 入楼相关

1. **战斗结束后才能入楼**：不要在战斗进行中写入楼层。战斗窗口是独立 iframe，写入楼层会干扰用户的聊天体验。

2. **`createChatMessages` 是异步函数**：需要 `await`。在 `commitBattle()` 流程中，入楼失败不应影响战斗提交本身 → 应使用 `try/catch` 包裹。

3. **`refresh: 'all'` 会触发 `CHAT_CHANGED` 事件**：这会导致楼层重新加载，可能有性能开销。但两种模式都只写 **1 条**消息，`'all'` 完全安全。

4. **不要重复入楼**：`commitBattle()` 可能被调用多次？需要加检查，确保同场战斗不会重复写入。可以在 `battle_session` 中添加 `chat_output_committed: boolean` 标志。

### 上下文注入相关

5. **读取楼层时要考虑 MVU 变量楼层**：如果某些楼层只有 MVU 数据没有对话文本（`message` 为空或很短），应该跳过或截断。

6. **上下文注入的 token 开销**：每场战斗都读取最近 5 楼，每次 AI 请求都带上 → 总 token 消耗会增加。`recent_floor_max_chars` 配置可以有效控制开销。

7. **不要在战斗过程中重复读取**：上下文注入应该在战斗**开始时**（`startBattle`）读取一次并缓存，而不是每回合都重新读取。或者设置为只在第一次构建 prompt 时读取。

8. **读取的楼层可能包含战斗相关的楼层**（如果玩家之前刚打完一场战斗）。需要排除包含战斗输出的楼层 → 可以通过排除 `role: 'assistant'` 且消息里包含战斗标记的楼层。

### 标签过滤相关

9. **酒馆没有内置的 `tag` 系统**：标签过滤只能通过 `data` 自定义字段或文本关键词匹配。文本匹配更可靠。

10. **排除关键词不宜过多**：每次注入都做关键词匹配有性能开销。建议列表不超过 10 个关键词。

### 数据一致性（已实现）

11. **`commitBattle()` 成功后 `battle_session` 被清空**：在 `commit.ts` 的 `editCanonicalState mutate` 的最后：
    ```typescript
    draft.battle_session = BattleSessionSchema.parse({}, { reportInput: true });
    ```
    这意味着一旦提交完成，`battle_session.runtime.history` 就不可用了。所以入楼逻辑必须在 `commitBattle()` 返回之前、从 session 中提取数据完成。

12. **✅ 已实现：入楼数据在 `editCanonicalState` 之前提取快照**：在 `commitBattleOutcome` 函数的 `mutate` 闭包中、清空 session 之前先 `klona(session.runtime.history)`：

    ```typescript
    // commit.ts L111-L112
    historySnapshot = klona(session.runtime.history);
    resolvedOutputMode = outputMode ?? session.output_mode;
    ```
    快照在闭包内捕获（此时 `session.runtime.history` 还完整），`editCanonicalState` 成功后写出。

### 与 MVU 变量框架的关系

13. **MVU 变量入楼是另一条路径**：当前系统在 `commitBattle()` 中通过 `editCanonicalState()` → `updateVariablesWith()` 将战斗结果写入源消息楼层的 `data.stat_data`。这与入楼（`createChatMessages`）**是两条独立的路径**：
    - MVU 变量路径：`commit.ts` → `state-access.ts` → `updateVariablesWith()` → 源消息楼层的 `data.stat_data`
    - 入楼路径：`commit.ts`(或 App.vue) → `createChatMessages()` → 新消息楼层
    - 两者不冲突，MVU 数据已经在 `data.stat_data` 中，入楼只是把对话内容写到 `message` 字段

14. **对 `stat_data` 的写入保持不变**：入楼功能不应该影响已有的 MVU 变量写入逻辑。战斗结束后，英雄属性、背包、世界事件等仍然通过 MVU 机制更新。

### 配置项设计

需要新增的配置项汇总（在 `BattleProfile.output` 中）：

```typescript
export type BattleOutputConfig = {
  round_narration_style: BattleNarrationStyle;
  full_battle_report_target_words: number;
  append_report_to_tavern_input: boolean;       // ← 已有，入楼开关可复用此字段或新增

  // 建议新增：
  output_to_chat: boolean;                       // 是否写入主聊天
  output_to_chat_mode: 'summary' | 'full';       // 摘要模式还是完整模式
  // （output_mode 已存在，用于区分 summary_only / full_log，但决定的是 commit 时 narrative 字段的选择）
};

export type BattleContextConfig = {
  // ... 现有字段
  include_floor_context: boolean;                // 启用历史上下文注入
  recent_floor_count: number;                    // 读取最近几楼（默认 3）
  recent_floor_max_chars: number;                // 截断字符数（默认 1500）

  filter_include_keywords: string[];             // 只保留包含这些关键词的楼层（为空表示全部保留）
};
```

### `output_mode` vs `output_to_chat_mode` 的区分

- **`battle_session.output_mode`** (`summary_only | full_log`)：**已有字段**，控制 `commitBattleOutcome` 中写入 `世界.近期事务` 的 narrative 文本是摘要还是完整日志。这是**世界事件层面的区分**，不是入楼层面的。
- **`output_to_chat_mode`** (`summary | full`)：**建议新增**，控制写入聊天楼层的格式。两种模式都只写 **1 条** assistant 消息，区别是 `summary`（合并 `history[].summary`）还是 `full`（合并 `history[].narration`）。
- 两者**可以不同步**：例如世界事件只记摘要（`summary_only`），但入楼写完整叙述（`full`）。
