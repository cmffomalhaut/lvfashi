## 文件
components/features/Settings/ApiSettings.tsx

## 作用
原项目里的 API 连接设置页：管理多供应商接口配置（OpenAI/Claude/Gemini/DeepSeek/智谱/自定义）、切换模型、设置 max_tokens/temperature、测试连接。

## 可借鉴
- 多供应商配置管理的 UI 组织方式（侧栏列surface → 详情编辑区）
- 模型输出推荐表（按模型名匹配建议 max_tokens 档位，这个思路战斗前端可以直接复用）
- 连接测试机制（发一次极短请求验证连通性）
- 模型列表动态获取（从 API 的 /v1/models 拉取）
- Token 档位预设 UI（8K/32K/64K 按钮组 + 自定义输入）

## 不适合直接搬
- 依赖原项目的类型定义（接口设置结构、单接口配置结构等）
- 假设独立前端宿主，样式系统基于 Tailwind + 自定义主题变量
- 代码量 728 行，大量是 UI 渲染，核心逻辑可剥离
- 温度/Token 预设是针对原项目场景的，战斗前端需重新设计

## 对当前战斗前端的价值
**高**

API/Key/模型配置页是战斗前端必须有的，这份代码的"多配置管理 + 模型推荐表 + 连接测试"思路可以直接参考。核心建议：战斗前端只需保留 1-2 个 API 配置槽位，不需要原项目那么多供应商。

## 文件
components/features/Settings/VariableManager.tsx

## 作用
运行时变量可视化编辑工具：左侧选择变量分区（角色/环境/世界/战斗/剧情等），右侧提供三种编辑模式——树状节点编辑、原始 JSON 编辑、高级路径命令（set/add/push/delete）。

## 可借鉴
- **树状变量编辑器组件（树节点编辑器）**：递归渲染对象/数组，支持展开折叠、新增字段/数组项、编辑值、删除。这个组件对"字段勾选树"极有参考价值
- 分区管理模式：按变量根键分区导航
- 原始 JSON 草稿编辑区 + 树编辑区同步
- 高级路径命令：action=set/add/push/delete + path + value，这正是战斗前端"路径→新值"模式

## 不适合直接搬
- 假设拥有完整 runtimeState（12 种分区），战斗前端只需要 stat_data
- onReplaceSection / onApplyCommand 直接作用于完整游戏状态
- 树节点编辑器的 prompt/alert 交互方式不适合战斗前端
- 需要适配 MVU 的消息楼层变量接口

## 对当前战斗前端的价值
**高**

树节点编辑器组件的递归设计、分区管理模式、高级路径命令机制，三个都是战斗前端"字段勾选树"和"路径写回"功能需要的。建议重点读树节点编辑器的递归渲染逻辑。

## 文件
hooks/useGame/promptRuntime.ts

## 作用
运行时 prompt 构建核心：选择 COT prompt（根据同人/女主规划等条件选不同版本）、按功能开关过滤 prompt 内容、剥离/注入特定 prompt、构建酒馆世界书文本、构建酒馆预设消息链（含占位符替换、消息角色映射、历史消息提取）。

## 可借鉴
- **Prompt 构建流水线思路**：按功能开关过滤 → 条件选择子 prompt → 变量替换 → 消息角色映射 → 同角色消息合并
- COT prompt 条件选择策略（switch 式的多条件分支）
- prompt 功能开关过滤模式（按 config 开关剥离或修改 prompt 内容）
- 占位符替换模式（`{{user}}`、`{{char}}`、`{{cot}}`）
- 酒馆消息后处理：system/user/assistant 角色映射与合并

## 不适合直接搬
- 深度耦合原项目 types（游戏设置结构、聊天记录结构、提示词结构等）
- 假设完整的酒馆预设模式（prompt_order、角色卡描述等）
- COT prompt 选择逻辑是原项目特有的（同人版/女主规划版等）
- 代码 751 行，大量逻辑无法直接复用

## 对当前战斗前端的价值
**中**

**思路值得参考，代码不可搬。** Prompt 构建流水线的"条件选择→开关过滤→变量替换→消息合并"模式对战斗前端写 prompt 有借鉴意义。但战斗前端需要的 prompt 构建逻辑要简单得多（主要是字段分析和战斗推演两种 prompt）。

## 文件
hooks/useGame/responseCommandProcessor.ts

## 作用
处理 AI 返回的 `tavern_commands` 命令数组：对每条 cmd（含 action=set/add/push/delete、key=路径、value=值），调用 `applyStateCommand` 依次更新 12 种游戏状态数据结构，最后做规范化 + 后校准 + 回写。

## 可借鉴
- **命令处理循环**：iterate commands → applyStateCommand → normalize → calibrate → write back
- `applyStateCommand` 的路径级操作机制（这个函数的实现在 stateHelpers.ts 里）
- 规范化流程：每次更新后都重新规范化各状态
- 命令后校准 hook（`deps.命令后校准`）：允许在校准阶段做修正

## 不适合直接搬
- 直接处理 12 种游戏状态，战斗前端只需要处理 stat_data
- 假设命令直接操作完整 State，战斗前端走"路径→新值"写回 MVU
- 依赖原项目的规范化函数族（规范化战斗状态、角色状态等）

## 对当前战斗前前的价值
**高**

"路径命令处理 + 规范化 + 后校准"这一机制与战斗前端"AI 返回路径→新值→前端写回 MVU"的设计高度匹配。建议深读 `applyStateCommand` 的具体实现（在 stateHelpers.ts 中），以及命令后校准机制。

## 文件
services/ai/chatCompletionClient.ts

## 作用
统一 AI 请求封装：支持 OpenAI 协议和 DeepSeek 协议；流式/非流式请求；SSE 解析；自动重试（指数退避 + 抖动）；Reasoner 模型 reasoning_content 提取；response_format 支持；自动检测并降级不支持的 stream；消息规范化与兼容修正。

## 可借鉴
- **SSE 流式解析器**（解析SSE文本）：处理事件流、累积 delta、[DONE] 信号
- **自动重试机制**（带重试执行）：指数退避 + 抖动 + 可中断
- 供应商自动识别（是否DeepSeek接口配置 / 是否Claude模型）
- 流式降级策略：检测到不支持 stream 时自动降级为非流式重新请求
- reasoning_content 处理：将 thinking 阶段的内容封装为 `<think>...</think>` 标签
- 消息规范化（规范化文本补全消息链）：同角色合并、过滤空内容
- response_format 自动检测支持性

## 不适合直接搬
- 代码 701 行，部分逻辑是图片生成相关的（从Markdown图片中提取DataUrl 等）
- 温度/Token 计算方式是针对原项目场景的
- 供应商识别逻辑（Zhipu/Doubao等）战斗前端可能不需要

## 对当前战斗前端的价值
**高**

**这是第一批文件里最值得深读的文件。** 战斗前端需要自己的 AI 请求封装，原项目的 chatCompletionClient 在 SSE 解析、自动重试、reasoning_content 处理、流式降级等方面都写得成熟稳健。建议全部通读，核心部分（SSE 解析、重试、reasoning_content 提取）可以直接参考实现。
